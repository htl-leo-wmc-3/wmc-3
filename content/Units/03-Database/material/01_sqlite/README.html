10  SQLite

Until now our data lived in files that we read completely into memory and wrote back completely on every change. That works for a dozen records. It does not work for a real application:

  • two requests writing at the same time can overwrite each other’s changes,
  • every query reads and scans the whole file,
  • nothing guarantees that a loan points at a book that actually exists.

A database solves all three. From DBI you already know relational databases and SQL; this unit is about using one from Node.js. We use SQLite.

10.1 Why SQLite

SQLite is not a server. It is a file plus a library that reads and writes it, and the library runs inside your own process. There is nothing to install, nothing to configure, no port and no password.

SQLite PostgreSQL, Oracle, SQL Server, …
Runs as a library inside your process a separate server process
The database is one file (library.db) files managed by the server
Setup none install, configure, create users
Writers at the same time one many
Good for embedded apps, tests, small and medium web apps multi-user production systems

SQLite is the most widely deployed database in the world: every phone in the room contains several, and many programs store their settings or save games in a SQLite file. It is also faster and more capable than its reputation; the SQLite team’s own guide considers it fine for websites with up to about 100,000 visits a day. Its one real limit is the single writer: many connections can read at the same time, but only one can write. It fits applications that read a lot and write a little, which describes most of our exercises.

💡 Install the SQLite Viewer extension for VS Code so you can look inside the .db file while you work. DB Browser for SQLite and DataGrip work as well.

10.2 The driver: node:sqlite

Node.js ships SQLite built in as the module node:sqlite. There is no npm install and nothing is compiled on your machine:

import { DatabaseSync } from "node:sqlite";

const db = new DatabaseSync("data/library.db"); // creates the file if it does not exist

Older projects use the packages better-sqlite3 or sqlite3. They work in a similar way, but they are extra dependencies with a native part that has to be built or downloaded during npm install, which is exactly what the built-in module avoids.

10.2.1 Database access is IO, and IO is asynchronous

A database is IO, just like reading a file or calling another server over the network. The chapter on asynchronous programming explained why IO must not block the single thread of Node.js, and for almost every database that is the rule: the driver sends the query to a database server and returns a Promise, and you await the result.

node:sqlite is the exception, and DatabaseSync says so in its name: every call blocks until it is finished. That is acceptable here for one reason only. SQLite runs inside our own process and works on a local file, so there is no network in between and a query takes microseconds, and the API becomes much simpler.

So from now on our services are synchronous: they return values, not Promises. Only explicit file access, for example reading a CSV file for an import, stays async. Keep in mind that this is a special case. With any database server you will be back to async and await.

10.3 Creating a schema

The tables are created with plain SQL. We keep the statements in a file data/schema.sql and execute it with db.exec(...), which runs several statements at once:

CREATE TABLE books (
  isbn   TEXT    NOT NULL,
  title  TEXT    NOT NULL,
  author TEXT    NOT NULL,
  year   INTEGER NOT NULL,
  CONSTRAINT pk_books PRIMARY KEY (isbn)
) STRICT;

CREATE TABLE loans (
  id      INTEGER NOT NULL,
  isbn    TEXT    NOT NULL,
  student TEXT    NOT NULL,
  CONSTRAINT pk_loans PRIMARY KEY (id),
  CONSTRAINT fk_loans_book FOREIGN KEY (isbn) REFERENCES books (isbn)
) STRICT;
  • Name your constraints (pk_books, fk_loans_book). When one is violated, the name tells you which rule was broken.
  • Order matters: loans refers to books, so books has to exist first, and when you drop the tables it is the other way round.
  • An INTEGER primary key gets its value from the database when you insert a row without it. That is how loans.id is filled.

10.3.1 Types and STRICT

SQLite has only a handful of types:

Type Used for
INTEGER whole numbers, and booleans as 0 / 1
REAL floating point numbers
TEXT strings, and dates as ISO strings (2026-11-24, 2026-11-24T10:15:00)
BLOB binary data, rarely needed

There is no date type and no boolean type. ISO dates are a good choice anyway: they sort correctly as strings, and SQLite’s date functions understand them.

Without STRICT, SQLite stores whatever you give it: 'abc' ends up in an INTEGER column without an error. STRICT at the end of CREATE TABLE switches that off, and the database then refuses values of the wrong type. We always use it.

10.3.2 Foreign keys: it depends on who opens the file

Three things the database now guarantees, which no amount of TypeScript could:

  • PRIMARY KEY: no two books with the same ISBN.
  • CHECK (...): a rule for the values of a column, for example CONSTRAINT ck_books_year CHECK (year > 0). It is the runtime counterpart of a union type.
  • FOREIGN KEY ... REFERENCES: a loan cannot point at a book that does not exist.

⚠️ SQLite itself does not enforce foreign keys by default, for historic reasons. Whether they are enforced depends on the program that opens the database: node:sqlite switches them on for every connection it opens, but the sqlite3 command line tool, many database viewers and other drivers do not. There, every connection has to switch them on itself:

db.exec("PRAGMA foreign_keys = ON");

We do not need this line, because node:sqlite already does it. If you ever use a different driver or tool and suddenly can insert a loan for a book that does not exist, this is why.

10.4 Using the driver

10.4.1 Statements without parameters

db.exec(schemaSql); // DDL, several statements at once, no result

10.4.2 Prepared statements

Everything else goes through a prepared statement: the SQL with ? placeholders, and the values passed separately when it runs.

const rows = db.prepare("SELECT * FROM books ORDER BY year").all(); // array of rows

const row = db.prepare("SELECT * FROM books WHERE isbn = ?").get("978-0132350884");
// one row, or undefined

const result = db
  .prepare("INSERT INTO loans (isbn, student) VALUES (?, ?)")
  .run("978-0132350884", "Ada");
console.log(result.changes); // 1 - number of rows affected
console.log(result.lastInsertRowid); // the id the database chose
Method Returns Use it for
all(...) an array of rows (maybe empty) queries with many results
get(...) one row or undefined queries for one row
run(...) { changes, lastInsertRowid } INSERT, UPDATE, DELETE

changes tells you how many rows a statement affected. That is how you tell “updated” from “there was no such row”, and therefore how a router decides between 200 and 404:

const result = db.prepare("UPDATE books SET title = ? WHERE isbn = ?").run(title, isbn);
if (result.changes === 0) {
  // no book with that isbn - this is not an error for the database
}

Values you pass must be strings, numbers, null or binary data. A boolean, a Date or undefined cannot be passed: convert them first (active ? 1 : 0, date.toISOString(), null).

10.4.3 Never build SQL with string concatenation

// NEVER do this. This is an SQL injection.
db.prepare(`SELECT * FROM books WHERE isbn = '${userInput}'`).all();

// Always do this.
db.prepare("SELECT * FROM books WHERE isbn = ?").all(userInput);

With a ? placeholder the value travels separately from the statement and can never be read as SQL. A user who sends 000' OR '1'='1 as an ISBN then simply gets no result. The next chapter shows what goes wrong otherwise.

10.4.4 Rows are not your objects

const row = db.prepare("SELECT * FROM loans WHERE id = ?").get(1);

The driver knows nothing about your types. row is a plain object whose keys are the column names (student, not studentName), it has no methods, and nothing has been checked. This is the same situation as with JSON.parse, and it has the same answer: a row type that describes the columns, and a function that turns a row into your model:

type BookRow = {
  isbn: string;
  title: string;
  author: string;
  year: number;
};

function toBook(row: BookRow): Book {
  return new Book(row.isbn, row.title, row.author, row.year);
}

const row = db.prepare("SELECT * FROM books WHERE isbn = ?").get(isbn) as BookRow | undefined;
const book = row === undefined ? undefined : toBook(row);

The as BookRow is a promise you make to the compiler, not a check. If a column can hold values that your model does not accept, validate them in the mapping function, exactly as you did with CSV lines.

💡 When you console.log a row, Node.js prints [Object: null prototype] { ... }. The driver creates rows without the usual object prototype. You can use them like any other object, and res.json(row) works. Only in tests compare them with toEqual, not toStrictEqual.

10.5 Transactions, the short version

Several statements that must all succeed or all fail belong in a transaction:

db.exec("BEGIN");
try {
  books.forEach((book) => insertBook.run(book.isbn, book.title, book.author, book.year));
  db.exec("COMMIT");
} catch (error) {
  db.exec("ROLLBACK");
  throw error;
}

If the fifth insert fails, the first four are undone as well. In this chapter we need that only to fill the database. A later chapter is all about when else you need a transaction, and why it is the core reason databases exist.

10.6 Where the connection lives

Opening the database for every query would be wasteful. The application opens it once, the first time it is needed, and keeps it open:

// src/db.ts
import { DatabaseSync } from "node:sqlite";
import { dirname, join } from "path";
import { fileURLToPath } from "url";

const dirName = dirname(fileURLToPath(import.meta.url));
export const dataDir = join(dirName, "..", "data");
export const dbPath = join(dataDir, "library.db");

let connection: DatabaseSync | undefined;

/** Opens the database, closing a previous one. Tests pass ":memory:". */
export function openDatabase(path: string = dbPath): DatabaseSync {
  if (connection !== undefined) {
    connection.close();
  }
  connection = new DatabaseSync(path);
  return connection;
}

/** The one connection of the application, opened on first use. */
export function getDb(): DatabaseSync {
  return connection ?? openDatabase();
}

Every function that needs the database calls getDb() and prepares its statement right there. Because the connection can be replaced, a test can open a fresh in-memory database (openDatabase(":memory:")) and the code under test does not notice.

One connection for the whole application is right for SQLite: the driver is synchronous, so only one statement runs at a time anyway, and SQLite allows only one writer. Database servers work differently. There, an application keeps a pool of connections and gives each request its own.

10.7 The database file is not committed

Do not commit the .db file. Put *.db into .gitignore and commit two things instead: the schema (data/schema.sql) and a seed script (npm run seed) that creates the database from scratch and fills it with sample data. Then anyone can recreate the database at any time, and you can always go back to a clean state.

⚠️ On Windows, a running server keeps the .db file open. Stop the server before you delete the file or run the seed script again.
