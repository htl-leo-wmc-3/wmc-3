10  SQLite

Until now our data lived in files that we read completely into memory and wrote back completely on every change. That works for twelve tools. It does not work for a real application: two requests writing at the same time lose data, every query is a full scan, and there is nothing to enforce that a loan points at a tool that actually exists.

A database solves all three. We use SQLite.

10.1 Why SQLite

SQLite is not a server. It is a file plus a library that reads and writes it. There is nothing to install, nothing to configure, no port, no password.

SQLite MySQL / PostgreSQL
Runs as a library inside your process a separate server process
The database is one file (workshop.db) a directory managed by the server
Setup none install, configure, create users
Concurrent writers one at a time many
Good for embedded apps, tests, small services multi-user production systems

It is the most widely deployed database in the world — every phone in the room contains several. For this unit it is perfect: the whole database is a file you can delete and recreate.

:bulb: Install the SQLite Viewer extension for VS Code so you can look inside the .db file while you work.

10.2 The driver

Node.js ships SQLite built in since version 22, as node:sqlite. No npm install, no native compilation:

import { DatabaseSync } from "node:sqlite";

const db = new DatabaseSync("data/workshop.db");

:warning: node:sqlite is synchronous — DatabaseSync says so in its name. This contradicts what the chapter on asynchronous programming said about never blocking the thread, and for a network database it would be unacceptable. For a local file it is a deliberate trade-off: the operations are measured in microseconds, and the API is far simpler.

We still declare our service functions async. Then the routers do not change, and the service can be swapped for an asynchronous driver later without touching anything else.

Other commonly used drivers are better-sqlite3 (synchronous, faster, needs a native build) and sqlite3 + sqlite (asynchronous). Both work; both have to be compiled during npm install, which is exactly the problem node:sqlite removes.

10.3 SQL we need

10.3.1 Creating a schema

CREATE TABLE IF NOT EXISTS tools (
  id        TEXT PRIMARY KEY,
  name      TEXT NOT NULL,
  category  TEXT NOT NULL CHECK (category IN ('power', 'hand', 'measuring', 'garden')),
  condition TEXT NOT NULL CHECK (condition IN ('good', 'worn', 'broken'))
);

CREATE TABLE IF NOT EXISTS loans (
  id       TEXT PRIMARY KEY,
  tool_id  TEXT NOT NULL REFERENCES tools (id),
  borrower TEXT NOT NULL,
  from_day TEXT NOT NULL,
  until    TEXT NOT NULL,
  state    TEXT NOT NULL CHECK (state IN ('open', 'returned'))
);

Three things the database now guarantees for you, which no amount of TypeScript could:

  • PRIMARY KEY — no two tools with the same id.
  • CHECK (… IN …) — the same constraint your union types express, but enforced at runtime.
  • REFERENCES tools (id) — a loan cannot point at a tool that does not exist.

:warning: SQLite only enforces foreign keys if you ask it to, per connection: db.exec("PRAGMA foreign_keys = ON"). Forgetting this is the classic SQLite mistake.

SQLite has very few types: TEXT, INTEGER, REAL, BLOB, NULL. There is no date type and no boolean. Store dates as TEXT in the format YYYY-MM-DD — it sorts correctly as a string — and booleans as INTEGER 0/1.

from and to are SQL keywords, which is why the column above is called from_day.

10.3.2 Queries

SELECT * FROM tools ORDER BY id;
SELECT * FROM tools WHERE category = ?;
SELECT * FROM tools WHERE id = ?;

INSERT INTO loans (id, tool_id, borrower, from_day, until, state) VALUES (?, ?, ?, ?, ?, ?);
UPDATE loans SET state = 'returned' WHERE id = ?;
DELETE FROM loans WHERE id = ?;

Filtering in WHERE instead of with filter in TypeScript is the point of using a database: the work happens where the data is, and an index can help.

-- the tools that are not lent out right now
SELECT t.* FROM tools t
WHERE t.condition <> 'broken'
  AND NOT EXISTS (SELECT 1 FROM loans l WHERE l.tool_id = t.id AND l.state = 'open');

10.4 Using the driver

10.4.1 Statements without a result

db.exec("PRAGMA foreign_keys = ON");
db.exec(schemaSql); // several statements at once

10.4.2 Prepared statements

const selectAll = db.prepare("SELECT * FROM tools ORDER BY id");
const rows = selectAll.all(); // an array of rows

const selectOne = db.prepare("SELECT * FROM tools WHERE id = ?");
const row = selectOne.get("t01"); // one row, or undefined

const insert = db.prepare("INSERT INTO loans (id, tool_id) VALUES (?, ?)");
const result = insert.run("l05", "t02"); // { changes, lastInsertRowid }
console.log(result.changes); // 1

changes tells you how many rows were affected — that is how you distinguish “updated” from “there was no such row”, and therefore how you decide between 200 and 404:

const result = db.prepare("UPDATE loans SET state = 'returned' WHERE id = ?").run(id);
if (result.changes === 0) {
  // no loan with that id
}

10.4.3 Never build SQL with string concatenation

// NEVER do this. This is an SQL injection.
db.exec(`SELECT * FROM tools WHERE id = '${userInput}'`);

// Always do this.
db.prepare("SELECT * FROM tools WHERE id = ?").get(userInput);

With ? placeholders the value is passed separately from the statement and can never be interpreted as SQL. A user who sends t01'; DROP TABLE tools; -- as an id then simply gets “not found”.

10.4.4 Rows are not your objects

const row = db.prepare("SELECT * FROM tools WHERE id = ?").get("t01");

row has the type unknown-ish and, at runtime, is a plain object whose keys are the column names — tool_id, not toolId. It has no methods. This is the same situation as JSON.parse, and it has the same answer: a row type plus a mapping function.

type ToolRow = {
  id: string;
  name: string;
  category: string;
  condition: string;
};

function toTool(row: ToolRow): Tool | undefined {
  return Tool.fromParts(row.id, row.name, row.category, row.condition);
}

Note that category is typed as string here, not as Category. The database CHECK constraint makes it very likely to be valid, but the driver cannot prove it — so we validate on the way in, exactly as we did with the CSV file.

10.5 Transactions

Several statements that must all succeed or all fail:

db.exec("BEGIN");
try {
  insertLoan.run(/* ... */);
  updateTool.run(/* ... */);
  db.exec("COMMIT");
} catch (error) {
  db.exec("ROLLBACK");
  throw error;
}

We need this only for the seeding script in the exercise, but it is the reason databases exist: either the whole change happens, or none of it.

10.6 Where the connection lives

Open the database once for the whole application, not per request:

// src/db.ts
import { DatabaseSync } from "node:sqlite";
import { dirname, join } from "path";
import { fileURLToPath } from "url";

const dirName = dirname(fileURLToPath(import.meta.url));

export const db = new DatabaseSync(join(dirName, "..", "data", "workshop.db"));
db.exec("PRAGMA foreign_keys = ON");

The module body runs once, the first time the module is imported. That is the simplest singleton there is.

:bulb: Do not commit the .db file. Add it to .gitignore and commit the schema plus a seeding script instead — then anyone can recreate the database from scratch, which is exactly what you want in a repository.
