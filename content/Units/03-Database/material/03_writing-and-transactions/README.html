12  Writing and Transactions

Reading data is half of an API. This chapter is about the other half: creating, changing and deleting rows, answering with the right status code, and making sure that an operation made of several statements happens completely or not at all. The examples use the parking garage from the previous chapter.

12.1 Inserting

const result = unit.run(
  "INSERT INTO cars (license_plate, model, owner) VALUES (:plate, :model, :owner)",
  { plate: "L-777XY", model: "Skoda Octavia", owner: "Eva Berger" }
);
// result.changes === 1, result.id === the id the database chose

Tables with an INTEGER primary key get their id from the database when you leave the column out. run reports it as id (the driver calls it lastInsertRowid), so you can return it to the client.

A successful POST answers 201 Created with the new resource in the body and its address in the Location header:

res.location(`/api/parkings/${parking.id}`).status(StatusCodes.CREATED).json(parking);

12.2 Updating and deleting

UPDATE and DELETE do not fail when no row matches. They just change nothing, and changes is 0. That is how you find out whether the resource existed:

const result = this.unit.run("DELETE FROM cars WHERE license_plate = :plate", { plate });
return result.changes === 1 ? "deleted" : "not-found";

A condition in the UPDATE can do part of the checking for you. A car can leave only once:

UPDATE parkings SET departed = :departed, fee = :fee
 WHERE id = :id AND departed IS NULL

changes === 0 now means “unknown id” or “already left”. One SELECT tells the two apart: 404 Not Found or 409 Conflict.

12.2.1 Deleting rows that others refer to

If parkings refer to a car, the foreign key decides what happens when the car is deleted:

Foreign key Deleting the car …
REFERENCES cars (license_plate) fails with “FOREIGN KEY constraint failed”
... ON DELETE CASCADE deletes its parkings as well
... ON DELETE SET NULL keeps the parkings, the column becomes NULL (it must be nullable)

Which one is right is a decision about the domain, not about SQL. For the garage, the history of a car that is removed from the system can go, so fk_parkings_car uses ON DELETE CASCADE. A car that is parked right now must not be deleted at all. That is a rule the service checks before deleting, and it answers 409.

12.3 Insert or update: ON CONFLICT

PUT /api/cars/L-777XY means “this car should look like this”, whether it exists or not. SQLite can do both in one statement, an upsert:

INSERT INTO cars (license_plate, model, owner) VALUES (:plate, :model, :owner)
ON CONFLICT (license_plate) DO UPDATE SET model = excluded.model, owner = excluded.owner

excluded is the row that could not be inserted. Whether the car was new (201) or updated (200) is not visible in the result, so the service checks with a SELECT first, inside the same transaction.

12.4 When a constraint says no

A violated constraint makes the statement throw. The error object carries an error code, and the helpers in db-errors.ts turn it into a question you can ask:

add(car: CarDto): CarDto | "exists" {
  try {
    this.unit.run(
      "INSERT INTO cars (license_plate, model, owner) VALUES (:plate, :model, :owner)",
      { plate: car.licensePlate, model: car.model, owner: car.owner }
    );
    return car;
  } catch (error) {
    if (isUniqueViolation(error)) {
      return "exists"; // the router answers 409 Conflict
    }
    throw error; // anything else is a real error: 500
  }
}

The alternative is to look first (SELECT 1 FROM cars WHERE license_plate = :plate) and insert only if nothing was found. Both work inside a transaction. The constraint stays the safety net either way: even a forgotten check cannot create a duplicate.

The status codes in short:

Situation Status
The request itself is invalid (missing field, wrong type, negative number) 400 Bad Request
The resource in the URL does not exist 404 Not Found
The request is fine, but conflicts with the current state (duplicate, already left, not enough stock) 409 Conflict

12.5 Validating the request body

req.body is whatever the client sent. The type you would like it to have is a wish, not a fact, so the router checks every field before it touches the database:

const { licensePlate, model, owner } = req.body ?? {};
if (typeof model !== "string" || model.trim().length === 0) {
  res.status(StatusCodes.BAD_REQUEST).json({ error: "model is required" });
  return;
}

Numbers arrive as numbers in JSON, but check them anyway: typeof quantity === "number", Number.isInteger(quantity), quantity > 0. Validation keeps nonsense away from the database. The database constraints catch what slips through.

12.6 Transactions

From DBI you know what a transaction guarantees: atomicity (all or nothing), consistency (constraints hold afterwards), isolation (others do not see half-finished work) and durability (committed is committed).

db.exec("BEGIN");
// ... several statements ...
db.exec("COMMIT"); // or ROLLBACK to undo everything since BEGIN

12.6.1 Every statement is atomic on its own

Without BEGIN, SQLite runs each statement in its own small transaction (autocommit). An UPDATE that changes ten rows changes all ten or none. So a single INSERT does not need a transaction. You need one as soon as several statements belong together:

Situation Transaction?
A request only reads no
A request runs exactly one writing statement not strictly, but we start one anyway, see below
A request writes several rows or tables that belong together yes
A request checks something and then writes based on the result (check-then-act) yes

12.6.2 Check-then-act

When a car arrives, the service checks that the spot is free and the car is not parked elsewhere, and then inserts the parking. Two things can go wrong without a transaction:

  • Half-finished work. If something fails after the first of several writes, the first one stays in the database. With a transaction, the rollback removes it.
  • Someone else changes the data between the check and the write. Our handlers are synchronous, and Node runs one at a time, so inside our own server two requests cannot interleave there today. That changes as soon as there is an await between check and write, or another process writes to the same database file: a second instance of the server, an import script, a person in a database tool. Then two cars can be checked into the same free spot.

A transaction makes the check and the write one unit. In SQLite only one connection can write at a time, and while our transaction holds the write lock, nobody else can change what we just checked.

12.6.3 Isolation in SQLite

SQLite transactions are serializable, the strictest level: there is only one writer at a time, and nobody sees changes that are not committed. A plain BEGIN is deferred: it takes the write lock only at the first writing statement. If another connection is writing at that moment, a transaction that already read something can fail halfway with “database is locked”. BEGIN IMMEDIATE takes the write lock at the start, so a transaction either cannot start or runs to the end. We always use it for writing.

12.7 The unit of work

Starting, committing and rolling back by hand in every route is repetitive, and forgetting the rollback in one error path leaves a transaction open. So we wrap it in a small class, Unit: one unit of work, everything one request does with the database.

Member Does
new Unit() uses the connection of the application (tests pass their own)
begin() BEGIN IMMEDIATE; throws if a transaction is already running
commit() / rollback() ends the transaction; throws if none is running
all<T>(sql, params) / get<T>(sql, params) queries with named parameters
run(sql, params) INSERT/UPDATE/DELETE, returns { changes, id }

12.7.1 using: the rollback you cannot forget

{
  using unit = new Unit();
  unit.begin();
  // ...
  unit.commit();
} // the end of the block: the unit is disposed

A variable declared with using instead of const is disposed when the block ends, whichever way it ends: normally, by return, or by an exception. Disposing means calling the object’s [Symbol.dispose]() method. Unit implements it: if a transaction is still open, it rolls it back. So the rule becomes very simple: nothing is stored unless the code reaches commit().

12.7.2 The router owns the unit

One request is one logical unit of work, so the router creates the unit, decides whether the request writes, and commits when everything worked. The services receive the unit in their constructor and only run statements:

parkingRouter.post("/parkings", (req, res) => {
  // ... validate the body, 400 otherwise

  using unit = new Unit();
  unit.begin(); // this request writes
  const result = new ParkingService(unit).arrive(licensePlate, spotId);

  if (result === "car-not-found" || result === "spot-not-found") {
    res.status(StatusCodes.NOT_FOUND).json({ error: result });
    return; // no commit -> rollback
  }
  if (result === "spot-occupied" || result === "car-already-parked") {
    res.status(StatusCodes.CONFLICT).json({ error: result });
    return; // no commit -> rollback
  }

  unit.commit();
  res.location(`/api/parkings/${result.id}`).status(StatusCodes.CREATED).json(result);
});
export class ParkingService {
  constructor(private readonly unit: Unit) {}

  arrive(
    licensePlate: string,
    spotId: number
  ): ParkingDto | "car-not-found" | "spot-not-found" | "spot-occupied" | "car-already-parked" {
    if (!new CarService(this.unit).exists(licensePlate)) {
      return "car-not-found";
    }
    // ... more checks, then the INSERT
  }
}

Why the router, and not each service?

  • No nested transactions. ParkingService uses CarService for a lookup. Both work with the same unit, so there is exactly one transaction. If every service method started its own, the second begin() would fail with “Transaction already started”.
  • The boundary is visible. One look at a route shows whether it writes and where it commits.
  • Tests decide where the data lives. A test creates a unit on an in-memory database and hands it to the service. The service does not notice.

The service still never sees Request or Response, and the router contains no SQL.

⚠️ No await between begin() and commit(). All requests share one connection. If a request pauses inside its transaction, the next request’s statements run on the same connection and end up in the same transaction. Read files and call other services before you begin, then do the database work in one synchronous block.

12.8 One connection here, a pool elsewhere

Our application keeps one connection open for its whole life. That fits SQLite: the driver is synchronous, there is only one writer anyway, and the transaction rules above keep requests apart. A database server is different. There, a request waits for the network, many requests run at the same time, and each transaction needs a connection of its own. Applications then keep a pool of connections and hand one to each request.
