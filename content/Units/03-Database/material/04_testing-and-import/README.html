The last two topics of the unit belong together: tests tell you that your services do what they should, and an import is the classic piece of code that you would never trust without them. The examples use the parking garage again.

13.1 Unit tests and integration tests

You know vitest from unit 02. With a database, there are two kinds of tests:

Unit test Integration test
Tests one function on its own a service together with the database
Example calculateFee(arrived, departed), parseCarLine(line), a validation helper ParkingService.arrive(...) with real SQL on real tables
Needs nothing but the function a database with the schema and known data
Finds wrong calculations, wrong rules wrong SQL, wrong joins, missing constraints, forgotten transactions

Write as much as possible as pure functions (input in, result out, no database, no clock): they are the easiest to test. Everything else is tested through the services. We do not test the routers with automated tests; requests.http covers them.

13.2 A database for every test

An integration test needs a database in a known state, and every test needs its own state. Otherwise a test that deletes a car breaks the next test that expects it. With SQLite this is cheap: a database can live entirely in memory.

// test/test-db.ts
import { readFileSync } from "fs";
import { DatabaseSync } from "node:sqlite";
import { Unit } from "../src/unit";

/** Reads a file relative to this test file, wherever the tests are started from. */
function readSql(relativePath: string): string {
  return readFileSync(new URL(relativePath, import.meta.url), "utf-8");
}

export function createTestDatabase(): DatabaseSync {
  const db = new DatabaseSync(":memory:");
  db.exec(readSql("../data/schema.sql")); // the REAL schema
  db.exec(readSql("./fixtures.sql")); // small, known data
  return db;
}

export function createTestUnit(): Unit {
  return new Unit(createTestDatabase());
}

:memory: creates a new, empty database that disappears when the connection is closed. Every call gives a fresh one, so tests cannot influence each other.

⚠️ Normally, integration tests run against a real database of the same kind as in production. A different database, or an imitation of one, behaves differently in exactly the details you want to test: types, constraints, locking, SQL dialect. That is why real projects start a test database server, often in a container. SQLite is the exception: the in-memory database is SQLite, the same library running inside the same process, with the same schema. So here it is the real thing, only faster.

13.2.1 Fixtures

The test data (test/fixtures.sql) is small and written by hand: three cars, four spots, a handful of parkings. Then every expected value in a test can be checked in your head (“two of the three cars are parked”). The large sample data of the application is the wrong choice. Nobody knows its numbers by heart, and changing it for the demo would break the tests.

13.3 Writing a test

import { beforeEach, describe, expect, test } from "vitest";
import { CarService } from "../src/car/car-service";
import { Unit } from "../src/unit";
import { createTestUnit } from "./test-db";

describe("CarService.remove", () => {
  let unit: Unit;

  beforeEach(() => {
    unit = createTestUnit();
  });

  test("refuses a car that is parked right now", () => {
    // arrange: the fixtures contain an open parking for L-200BB

    // act
    const result = new CarService(unit).remove("L-200BB");

    // assert
    expect(result).toBe("still-parked");
    expect(new CarService(unit).exists("L-200BB")).toBe(true);
  });
});
  • Arrange, act, assert: prepare the state, do one thing, check the outcome.
  • One behaviour per test, and a name that says it. When it fails, the name tells you what is broken.
  • Check the database, not only the return value. After a refused write, look whether really nothing changed.
  • Test the refusals as carefully as the success: "not-found", "exists", "still-parked" are part of what the service promises.
  • When you expect an exception, say which one: toThrow(/CHECK constraint failed/). A bare toThrow() also passes when the code fails for a completely different reason.

13.3.1 Time in tests

arrive stores the current time, depart calculates a fee from it. A test cannot know what “now” will be when it runs, so the services take the time as a parameter with a default:

arrive(plate: string, spotId: number, now: string = nowText()): ArriveResult

The router calls arrive(plate, spotId) and gets the real time. A test calls arrive("L-300CC", 4, "2026-12-01 08:00:00") and knows exactly what will be stored.

13.3.2 Testing transactions

A missing commit() is invisible in requests.http: the response looks fine, and only later you notice that nothing was stored. A test finds it right away. Use one database and two units:

test("an arrival that is not committed is gone afterwards", () => {
  const db = createTestDatabase();

  {
    using unit = new Unit(db);
    unit.begin();
    new ParkingService(unit).arrive("L-300CC", 4, "2026-12-01 08:00:00");
  } // no commit -> disposed -> rolled back

  using check = new Unit(db);
  expect(new CarService(check).isParked("L-300CC")).toBe(false);
});

13.4 Importing data from a file

Applications often start with data from somewhere else: a CSV export, a list from another system. An import has three steps, and they should stay separate:

  1. Read the file. That is real IO, so it is async, and it happens before the transaction begins.
  2. Parse and validate every line in a pure function. It returns either the data or an error message, so it is easy to unit test.
  3. Store the valid rows in one unit of work.
const text = await readFile(join(dataDir, "cars.csv"), "utf-8"); // 1. read, async

const lines = text.split(/\r?\n/).slice(1); // without the header
const cars: CarDto[] = [];
const errors: string[] = [];
lines.forEach((line, index) => {
  if (line.trim().length === 0) {
    return;
  }
  const result = parseCarLine(line); // 2. parse: CarDto or an error message
  if (typeof result === "string") {
    errors.push(`line ${index + 2}: ${result}`);
  } else {
    cars.push(result);
  }
});

using unit = new Unit(); // 3. store, synchronous, one transaction
unit.begin();
const report = new CarImportService(unit).importCars(cars);
unit.commit();

\r?\n handles files with Windows line endings, and empty lines are skipped. Line numbers in the messages count the header, so they match what the user sees in an editor.

13.4.1 All or nothing, or skip and report?

What should happen when line 37 is a duplicate?

Strategy Behaviour Fits
All or nothing the first error stops the import, the transaction is rolled back, nothing is stored data that only makes sense complete (an order with its items, a timetable)
Skip and report invalid or duplicate lines are skipped, the rest is stored, and the report lists every skipped line lists of independent records (cars, passengers)

Both need the transaction. For “all or nothing” that is obvious. For “skip and report” it still makes sure that a crash halfway through, a programming error or a full disk, does not leave half an import behind.

💡 When a single statement inside a transaction violates a constraint, SQLite undoes only that statement. The transaction stays open, and the earlier inserts are still in it. That is what makes “skip and report” with isUniqueViolation possible inside one unit.

⚠️ The file is read before begin(). An await inside the transaction would pause it, and other requests would run their statements on the same connection, inside your transaction.
