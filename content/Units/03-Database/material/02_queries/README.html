You know SELECT, joins and GROUP BY from DBI. This chapter is about running such queries from TypeScript safely, and about turning what comes back into something an API can return. All examples use the database of a small parking garage:

Table Columns
cars license_plate (PK), model, owner
spots id (PK), floor, number, kind (regular, electric, accessible)
parkings id (PK), spot_id (FK), license_plate (FK), arrived, departed (NULL while the car is still there), fee

11.1 SQL injection

Imagine a login that checks the user name and password like this:

// NEVER do this
const sql = `SELECT COUNT(*) AS found FROM users
              WHERE name = '${name}' AND password = '${password}'`;
const row = getDb().prepare(sql).get() as { found: number };

A user who types x' OR '1'='1 as the password turns the statement into

SELECT COUNT(*) AS found FROM users WHERE name = 'admin' AND password = 'x' OR '1'='1'

AND binds stronger than OR, so the condition is true for every row, and the attacker is logged in without knowing any password. With other input they can read other tables, change data or delete it (the classic comic). This is SQL injection, and it is still one of the most common security holes in web applications.

The cause is always the same: a value from the outside became part of the SQL text. The fix is always the same as well: a prepared statement with placeholders.

const row = getDb()
  .prepare("SELECT COUNT(*) AS found FROM users WHERE name = ? AND password = ?")
  .get(name, password) as { found: number };

The statement is compiled first, and the values are passed separately. Whatever the user types is compared as a string and can never change the structure of the statement.

⚠️ Do not try to “clean” input yourself by removing quotes or similar. You will miss a case, and the library already does it correctly. Every value that comes from a request, a file or another system goes in as a parameter. No exceptions, also not for numbers.

💡 Storing passwords as plain text, as in the example, is a second serious mistake. Passwords are stored as salted hashes, a topic for later.

11.2 Parameters: ? and :name

Placeholders come in two forms:

// positional: the values in the same order as the question marks
getDb().prepare("SELECT * FROM spots WHERE floor = ? AND kind = ?").all(1, "electric");

// named: one object, the keys are the names
getDb()
  .prepare("SELECT * FROM spots WHERE floor = :floor AND kind = :kind")
  .all({ floor: 1, kind: "electric" });

Named parameters are easier to read once a statement has more than two or three of them, and the same name can appear twice in the statement.

⚠️ The names in the statement and the keys of the object must match. A key that the statement does not contain makes node:sqlite throw (“Unknown named parameter”). The other way round it stays silent: if the object has no key for :kind, the driver uses NULL for it, and the query quietly returns nothing.

Only values can be parameters. Table names, column names, ASC/DESC and other keywords cannot. When they depend on the request, they come from a fixed list, see “Sorting” below.

11.3 What comes back

get(...) returns one row or undefined, all(...) an array of rows. The values arrive as JavaScript types:

SQLite TypeScript
INTEGER, REAL number
TEXT string
NULL null

A row’s keys are the names of the result columns. Give computed columns a name with AS, and choose names in camelCase, so the row already has the shape your API returns:

type FloorOccupancy = {
  floor: number;
  totalSpots: number;
  occupied: number;
};

const rows = getDb()
  .prepare(
    `SELECT s.floor AS floor, COUNT(*) AS totalSpots, COUNT(p.id) AS occupied
       FROM spots s
       LEFT JOIN parkings p ON p.spot_id = s.id AND p.departed IS NULL
      GROUP BY s.floor
      ORDER BY s.floor`
  )
  .all() as FloorOccupancy[];

When a row has the table’s column names (license_plate), map it to your own type with a small function, as in the previous chapter.

11.4 Filtering

11.4.1 A WHERE built from fragments

Optional filters from the query string mean a WHERE clause whose parts depend on the request. Build it from fixed text fragments, and collect the values separately:

export function findFreeSpots(floor?: number, kind?: SpotKind): Spot[] {
  const conditions = [
    "NOT EXISTS (SELECT 1 FROM parkings p WHERE p.spot_id = s.id AND p.departed IS NULL)",
  ];
  const values: (string | number)[] = [];

  if (floor !== undefined) {
    conditions.push("s.floor = ?");
    values.push(floor);
  }
  if (kind !== undefined) {
    conditions.push("s.kind = ?");
    values.push(kind);
  }

  const sql = `SELECT * FROM spots s
                WHERE ${conditions.join(" AND ")}
                ORDER BY s.floor, s.number`;
  return getDb().prepare(sql).all(...values) as Spot[];
}

The SQL text only ever contains what you wrote yourself. Everything from the request is in values.

11.4.2 LIKE

LIKE compares with a pattern: % stands for any number of characters, _ for exactly one. The wildcards belong in the value, not in the SQL:

getDb()
  .prepare("SELECT * FROM cars WHERE owner LIKE ? ORDER BY owner")
  .all(`%${owner}%`); // contains `owner`

SQLite’s LIKE ignores the difference between upper and lower case, but only for the 26 ASCII letters: a matches A, ä does not match Ä. If that matters, compare LOWER(owner) with a lowercased value. (A user who types % themselves gets “everything”, which is harmless here.)

11.5 Sorting and limiting

ORDER BY ? does not work: the placeholder would be a value, and sorting by a constant value does nothing. The column has to be part of the SQL text, so it must never come from the request directly. Map the allowed values to columns instead:

// model.ts
export type CarSort = "plate" | "owner" | "model";

export function isCarSort(value: string): value is CarSort {
  return value === "plate" || value === "owner" || value === "model";
}

// car-service.ts
const SORT_COLUMNS = {
  plate: "license_plate",
  owner: "owner",
  model: "model",
};

export function findCars(owner: string, sort: CarSort): CarDto[] {
  const column = SORT_COLUMNS[sort];
  const rows = getDb()
    .prepare(`SELECT * FROM cars WHERE owner LIKE ? ORDER BY ${column}, license_plate`)
    .all(`%${owner}%`) as CarRow[];
  return rows.map(toDto);
}

The router checks the request’s sort with isCarSort and answers 400 for anything else, so the service only ever receives one of the three keys. The SQL text still only contains strings you wrote. LIMIT ? on the other hand is a value and works as a parameter, but check the number in the router first: a positive integer, with an upper bound.

11.6 Joins

An inner join returns only rows that have a partner on both sides:

SELECT p.arrived, p.departed, p.fee, s.floor, s.number
  FROM parkings p
  JOIN spots s ON s.id = p.spot_id
 WHERE p.license_plate = ?
 ORDER BY p.arrived DESC

A left (outer) join keeps every row of the left table, and fills the columns of the right table with NULL where there is no partner. That is what you need for “all floors, and how many cars are on each”, including floors that are empty:

SELECT s.floor, COUNT(*) AS totalSpots, COUNT(p.id) AS occupied
  FROM spots s
  LEFT JOIN parkings p ON p.spot_id = s.id AND p.departed IS NULL
 GROUP BY s.floor

⚠️ ON or WHERE? The condition p.departed IS NULL is part of the join here: “join only the parkings that are still running”. Moved into a WHERE, it is applied after the join. A spot whose cars have all left joins only rows with a departed date, the WHERE removes them all, and the spot disappears from the result. totalSpots is then wrong. Rule of thumb: conditions on the right table of a LEFT JOIN go into ON.

A table can also be joined with itself, for example employees with their manager, who is another employee. Give the table two aliases, and use a LEFT JOIN so the boss, who has no manager, is not lost.

11.7 Grouping and aggregates

Function Result
COUNT(*) number of rows in the group
COUNT(column) number of rows where column is not NULL
COUNT(DISTINCT column) number of different values
SUM, AVG, MIN, MAX as the name says; NULL if there were no values
ROUND(x, 2) rounded to 2 decimal places
COALESCE(x, 0) x, or 0 if x is NULL

In the occupancy query above, COUNT(*) counts all spots of a floor, while COUNT(p.id) counts only those that found a current parking. The outer join produced NULL for the others.

WHERE filters rows before they are grouped, HAVING filters groups afterwards:

SELECT c.owner, COUNT(*) AS parkings
  FROM cars c
  JOIN parkings p ON p.license_plate = c.license_plate
 WHERE p.departed IS NOT NULL      -- only finished parkings
 GROUP BY c.owner
HAVING COUNT(*) >= ?              -- only regular customers
 ORDER BY parkings DESC

⚠️ Joining two “many” sides at once multiplies rows. If a floor has 8 spots and you join both the spots and all past parkings, every spot appears once per parking, and COUNT(*) no longer counts spots. COUNT(DISTINCT s.id) counts them correctly again, or you compute one of the numbers in a subquery.

An aggregate without GROUP BY returns exactly one row. SUM over no rows is NULL, not 0, so a revenue query for a day without any parking needs COALESCE(SUM(fee), 0).

11.8 Subqueries

A query inside a query. The most useful forms for us:

-- cars that have never parked
SELECT * FROM cars c
 WHERE NOT EXISTS (SELECT 1 FROM parkings p WHERE p.license_plate = c.license_plate);

-- spots on the floor with the most electric spots
SELECT * FROM spots
 WHERE floor = (SELECT floor FROM spots WHERE kind = 'electric'
                 GROUP BY floor ORDER BY COUNT(*) DESC LIMIT 1);

EXISTS / NOT EXISTS asks “is there at least one matching row?” and is often the clearest way to write a condition about another table. A subquery in = must return exactly one value.

11.9 Dates

SQLite stores dates as TEXT, and its date functions work on ISO strings:

Expression Result
date('2026-11-24 14:30:00') '2026-11-24'
strftime('%Y', arrived) the year as text, '2026'
date('now') today (in UTC)
julianday(departed) - julianday(arrived) the difference in days, as a decimal number

Because ISO strings sort correctly, you can compare them directly. Be careful with ranges: departed <= '2026-11-30' misses '2026-11-30 17:00:00', because the longer string is “greater”. Compare the date part instead:

SELECT date(departed) AS day, COUNT(*) AS parkings, ROUND(SUM(fee), 2) AS revenue
  FROM parkings
 WHERE date(departed) BETWEEN ? AND ?   -- inclusive on both ends
 GROUP BY date(departed)
 ORDER BY day

11.10 Validating query parameters

Everything in req.query is a string, an array or missing. Check it in the router, before the service is called, and answer 400 Bad Request if it does not fit:

carRouter.get("/cars", (req, res) => {
  const owner = singleValue(req.query.owner) ?? "";
  const sort = singleValue(req.query.sort) ?? "plate";

  if (!isCarSort(sort)) {
    res.status(StatusCodes.BAD_REQUEST).json({ error: "sort must be plate, owner or model" });
    return;
  }
  res.json(findCars(owner, sort));
});
  • Numbers: Number(text), then Number.isInteger(...) and a range check.
  • Dates: a simple pattern (/^\d{4}-\d{2}-\d{2}$/) and, for ranges, from <= to.
  • Fixed sets of values (kind): a type guard such as isSpotKind(value).

The parameters protect you against injection. The validation protects you against nonsense, and gives the client a clear answer instead of an empty list.
