9  Objects, Types and Classes

You have met classes, inheritance and interfaces before. This chapter is about the parts TypeScript does its own way — and about when a class is the wrong tool and a plain type is the right one.

9.1 Object literals

In JavaScript an object is created without a class. It is a bag of key/value pairs:

const act = {
  id: "a01",
  name: "Kernel Panic",
  durationMinutes: 60,
};

console.log(act.name);
console.log(act["name"]); // the same thing

TypeScript infers the type of act from the literal. You can also name that type:

type Act = {
  id: string;
  name: string;
  durationMinutes: number;
  encore?: boolean; // optional -> boolean | undefined
  readonly createdAt: string; // may only be set once, when the object is created
};

This is the workhorse of the unit. Most “objects” in our APIs are plain data with a type — no class needed.

9.2 Structural typing (duck typing)

The single most important rule of the type system. TypeScript compares types by their shape, not by their name. Two types with the same members are the same type, even if they were declared separately and never mention each other.

type Point = { x: number; y: number };
type Coordinate = { x: number; y: number };

const p: Point = { x: 1, y: 2 };
const c: Coordinate = p; // fine. Same shape = same type.

Nothing has to implement anything. If it walks like a duck, it is a duck:

type Named = { name: string };

function greet(thing: Named) {
  console.log(`Hello ${thing.name}`);
}

const user = { name: "Ada", age: 36 };
greet(user); // fine - it HAS a name
greet(new Tool("t1", "Hammer")); // fine, if Tool has a `name` property

9.2.1 Excess property check

There is one exception that confuses everyone once:

const named: Named = { name: "Ada", age: 36 }; // ERROR: 'age' does not exist in 'Named'

const thing = { name: "Ada", age: 36 };
const named2: Named = thing; // fine!

A literal assigned directly is checked strictly, because extra properties there are almost always a typo. A value that already has a type is only checked for compatibility.

9.3 type or interface?

Both describe a shape, and for objects they are nearly interchangeable.

type interface
Objects yes yes
Unions ("a" \| "b") yes no
Tuples, function types yes awkward
Can be re-opened / merged no yes
extends via & yes

Convention for this unit: use type everywhere. Use interface only when you really want a contract that several classes implement. Do not prefix interface names with I; TypeScript does not do that.

9.4 Classes

The syntax will look familiar. Three details are worth memorising, because they differ from what you would expect.

export class Tool {
  // 1. no access modifier means PUBLIC - there is no "internal"
  readonly id: string;
  readonly name: string;
  private timesLent = 0; // type inferred from the initialiser

  static readonly MAX_LOAN_DAYS = 14; // 2. no `const` in a class - use `static readonly`

  constructor(id: string, name: string) {
    this.id = id;
    this.name = name;
  }

  // 3. `get` is a method with a keyword, and it is called WITHOUT parentheses
  get isPopular(): boolean {
    return this.timesLent > 10;
  }

  lend(): void {
    this.timesLent++;
  }
}

const tool = new Tool("t1", "Cordless drill");
console.log(tool.isPopular); // no ()

9.4.1 Parameter properties

The constructor boilerplate above has a short form:

export class Tool {
  constructor(
    readonly id: string,
    readonly name: string,
    private timesLent = 0
  ) {}
}

The modifier in the parameter list declares the field and assigns it. There is no other short form for this, and you will see it in a lot of TypeScript code.

9.4.2 private is not a security feature

class A {
  private secret = 42; // compile-time only - visible at runtime
  #reallySecret = 43; // truly private, enforced by the JavaScript runtime
}

private is erased with everything else during transpilation. (a as any).secret reads it without complaint. For our purposes private is fine — just do not mistake it for protection.

9.4.3 Static factory methods

A constructor cannot fail gracefully, cannot be async and cannot have overloads. The usual answer is a static factory:

export class Tool {
  private constructor(readonly id: string, readonly name: string) {}

  /** Returns undefined instead of throwing when the line is malformed. */
  static fromCsvLine(line: string): Tool | undefined {
    const [id, name] = line.split(";");
    return id && name ? new Tool(id, name) : undefined;
  }
}

Note the private constructor: it forces everyone through the factory, so the validation cannot be skipped. You will use this pattern in EX4.

9.4.4 Inheritance

class FullDayLoan extends Loan {
  constructor(id: string, toolId: string) {
    super(id, toolId); // must be called first
  }

  override describe(): string {
    // `override` is optional but recommended
    return `${super.describe()} (full day)`;
  }
}

abstract class, abstract members and implements all exist and behave as you expect. instanceof works at runtime, because classes — unlike interfaces and types — do survive transpilation.

We use inheritance sparingly in this unit. Prefer a union of types with a discriminating field:

type Loan =
  | { kind: "open"; toolId: string; since: string }
  | { kind: "returned"; toolId: string; since: string; until: string };

function describe(loan: Loan): string {
  // TypeScript narrows on `kind` - inside each branch the type is exact
  return loan.kind === "returned"
    ? `returned on ${loan.until}`
    : `open since ${loan.since}`;
}

This is a discriminated union, and it replaces a lot of small class hierarchies.

9.5 Classes vs. plain objects

Use a class when Use a type when
there is behaviour, not just data it is pure data
there are invariants to protect it comes from JSON or goes into JSON
you need instanceof you need a DTO

Remember from 03_async-and-files:

const tools = JSON.parse(text) as Tool[]; // NOT Tool instances - no methods!

JSON.parse produces plain objects. as Tool[] only silences the compiler; calling a method on one of them crashes at runtime. If you want real instances, construct them:

const tools = (JSON.parse(text) as ToolDto[]).map((dto) => Tool.fromDto(dto));

This is the toDto/fromDto pattern, and it is the heart of EX4.

9.6 Map and Set

const byId = new Map<string, Tool>();
byId.set(tool.id, tool);
const found = byId.get("t1"); // Tool | undefined
byId.has("t1");
byId.delete("t1");
byId.size; // a property, not a method

for (const [id, tool] of byId) {
  // ...
}
const all = [...byId.values()];

A Map holds key/value pairs, a Set holds each value at most once. Build a Map from an array in one step:

const byId = new Map(tools.map((tool) => [tool.id, tool]));

:warning: A plain object ({}) also maps keys to values, but its keys are always strings, it inherits properties from Object.prototype, and it has no size. Use Map whenever the keys are data.

9.7 Equality

"1" == 1; // true  - == converts types. Never use it.
"1" === 1; // false - === compares type and value. Always use this.

({ a: 1 } === { a: 1 }); // false - reference comparison

There is no operator overloading, and no built-in convention for value equality. If you need it, write an equals method and call it explicitly.
